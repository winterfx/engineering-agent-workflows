02 · Concurrency

整体并行，
同一目标串行。

并行策略提升不同 Issue 和 PR 的吞吐；锁与 fingerprint 则避免同一目标被同时写坏。

哪些能同时发生？

两套 agent 都配置为 concurrency_policy: parallel。

不同 Issues parallel
不同 Draft PRs parallel
同一 Issue 实现 locked
同一 PR 修复 locked

仓库的 daemon 示例给 GitHub Issue / Comment 队列各 4 个 workers。 同一 Issue workspace 和同一 PR review 使用各自的锁；内容变化还会由 fingerprint / head SHA 拒绝过期结果。

实现、验证并创建 Draft PR

可信工具抢占 Issue lock、clone 默认分支；Agent 修改代码并增加回归测试。外层验证 diff 后 commit、push，创建 Draft PR #440。

只有高风险改动才暂停批准

若涉及认证、迁移、CI/release 或超出规模限制，流程停在 agent:needs-approval。维护者审查风险后添加 agent:approved，Agent 才会重新实现；本例为低风险，因此跳过。

05 MonkeyScan

扫描 Draft PR 并留下 finding

MonkeyScan 在 PR conversation、review 或 inline comment 中报告一个可验证的问题，例如错误路径仍可能重复返回事件。

review comment · created
06 Draft PR

在全新 sandbox 中验证并修复

Agent 从 PR 当前 head 重新 clone，验证 finding 后修改代码和测试；同一批 finding 合并为一个 commit，并非盲目接受扫描结论。

最终评审并决定是否合并

维护者检查完整 diff、测试和 MonkeyScan 修复结果，再决定标记 ready 或 merge。Workflow 永远不会替维护者完成这一步。

04 · Boundaries

Agent 负责理解和修改，
代码负责信任与写入。

01 凭据隔离

两个 Agent 都看不到 GitHub / GitLab token；Provider 操作只在可信外层进行。

02 默认 dry-run

Triage 只给提案；Draft PR 会验证临时 diff，但不改 label、branch 或 PR。

03 拒绝过期结果

Issue fingerprint、base commit 和 PR head SHA 在写入前都会重新核对。

04 不自动合并

只创建 Draft PR；绝不 merge、不标记 ready、不关闭或改写 Issue 内容。

并行处理事件，
串行通过信任。

自动化负责减少重复劳动；从“理解问题”进入“修改代码”的那一步，始终由维护者决定。
